## 1. Паспортная часть и общие положения

### 1.1 Назначение документа

Регламент технического обслуживания (ТО) — нормативно-технический документ, который определяет план, периодичность, содержание работ и зоны ответственности при поддержании работоспособности `perfect-numbers-tool`.

Цели внедрения регламента:

- минимизировать простои и время восстановления после сбоев;
- предотвратить потерю и повреждение истории сканирований числовых осей;
- обеспечить воспроизводимость результатов и актуальность документации;
- обеспечить безопасность данных (контроль целостности, хранение копий на отдельном носителе).

### 1.2 Область применения

| Объект | Состав |
|---|---|
| **Программное обеспечение** | Пакет `perfect_numbers` (модули `core`, `io_handlers`, `backup`, `cli`), версия 1.0.0 |
| **Данные** | Файл истории `data/history.json`; резервные копии `backups/history_*.json` и манифесты `*.manifest` |
| **Окружение** | Python 3.10+ (Windows / Linux / macOS), Git, GitHub (репозиторий и CI) |
| **Документация** | ТЗ, README (ru/en), тест-кейсы, правила Git, настоящий регламент |

Аппаратная часть — любой ПК, поддерживающий Python 3.10+; специального оборудования нет. Регламент не распространяется на ОС и оборудование рабочего места.

### 1.4 Виды технического обслуживания

| Вид | Описание | Раздел |
|---|---|---|

> Правило хранения 3-2-1: **3** копии данных, на **2** разных носителях, **1** — вне основного рабочего места.

### 1.5 Параметры хранения

| Параметр | По умолчанию | Рекомендация |
|---|---|---|
| `--data-file` | `data/history.json` | Каталог на надёжном диске |
| `--backup-dir` | `backups` | Отдельный диск или каталог, не совпадающий с каталогом истории |
| `--keep` | 10 | 10–30; размер каждой копии примерно равен размеру истории |

Каталоги `data/` и `backups/` исключены из Git (`.gitignore`): это пользовательские данные, а не исходный код.

## 2. Технологические карты ТО

### 2.1 Плановое (профилактическое) ТО

| № | Наименование операции | Периодичность | Пошаговый алгоритм и ожидаемый результат | Инструменты | Вид |
|---|---|---|---|---|---|
| **ТК-01** | Создание резервной копии истории | Ежедневно при активной работе; обязательно перед важными изменениями истории | 1. Выполнить `python -m perfect_numbers backup`. 2. Убедиться в сообщении «Копия создана: …». **Результат:** код 0, в `backups/` появились `history_*.json` и `.manifest`; число копий не больше `--keep` | CLI программы | Плановое |
| **ТК-02** | Проверка целостности всех копий | Еженедельно | 1. Выполнить `python -m perfect_numbers verify`. 2. Прочитать итоговую строку. **Результат:** «повреждено: 0», код 0. При коде 3 — перейти к ТК-10 | CLI программы (SHA-256, манифесты) | Плановое |
| **ТК-03** | Проверка свободного места и размера каталогов | Еженедельно | 1. Проверить свободное место на диске с `data/` и `backups/` (проводник / `df -h`). 2. Сравнить объём `backups/` с ожидаемым ≈ (`--keep` + 1) × размер истории. **Результат:** свободно не менее 100 МБ и не менее 10-кратного объёма `backups/`; число копий ≤ `--keep` | Средства ОС, `list-backups` | Плановое |
| **ТК-04** | Контрольное восстановление (учения) | Ежемесячно | 1. Выполнить восстановление в тестовый каталог: `python -m perfect_numbers restore --data-file /tmp/drill/history.json --backup-dir backups`. 2. Проверить `python -m perfect_numbers history --data-file /tmp/drill/history.json`. **Результат:** история восстановлена, записи соответствуют ожидаемым; рабочая история не затронута | CLI программы | Плановое |
| **ТК-05** | Запуск автотестов | Ежемесячно и после любых изменений кода | 1. В корне проекта: `python -m unittest discover -s tests`. **Результат:** «OK», 68 из 68 тестов пройдены | `unittest` / `pytest` | Плановое |
| **ТК-06** | Копирование каталога `backups/` на внешний носитель | Ежеквартально (при активной работе — ежемесячно) | 1. Скопировать `backups/` на второй носитель (флеш-накопитель, облако, сетевой диск). 2. Запустить `verify` с `--backup-dir` копии. **Результат:** копия каталога на втором носителе, `verify` — «повреждено: 0» | Проводник / `cp`, CLI программы | Плановое |
| **ТК-07** | Проверка совместимости с актуальной версией Python и CI | Ежеквартально | 1. Проверить `python --version`. 2. Убедиться, что последний запуск GitHub Actions (Windows, Linux, macOS; Python 3.10–3.13) зелёный. **Результат:** тесты проходят на поддерживаемых версиях | GitHub Actions, `python --version` | Плановое |
| **ТК-08** | Актуализация документации и релиз | При каждом релизе | 1. Обновить версию в `pyproject.toml` и `__init__.py`. 2. Обновить ТЗ, README (ru и en), тест-кейсы при изменении поведения. 3. Создать тег `vX.Y.Z` и отправить в GitHub (см. [GIT.md](GIT.md)). **Результат:** тег и документация соответствуют версии | Git, GitHub | Плановое |

### 2.2 Внеплановое (инцидентное) ТО

| № | Инцидент / признак | Пошаговый алгоритм и ожидаемый результат | Инструменты | Вид |
|---|---|---|---|---|
| **ТК-09** | История повреждена: «Ошибка хранилища: Файл истории повреждён…», код 3 | 1. Прекратить запись в историю, файлы вручную не удалять. 2. `python -m perfect_numbers list-backups` — найти последнюю копию со статусом OK. 3. `python -m perfect_numbers restore` (из самой свежей) или `restore --file backups/history_<…>.json`. 4. `python -m perfect_numbers history` — проверить результат. **Результат:** история восстановлена, код 0; повреждённый файл сохранён как `history.json.corrupt-<время>` для разбора | CLI программы | Внеплановое |
| **ТК-10** | Копия повреждена: «Контрольная сумма не совпадает», «Манифест копии не найден», `verify` вернул код 3 | 1. Определить повреждённую копию по списку `verify`. 2. Не использовать её для восстановления (программа отклонит её, хранилище останется нетронутым). 3. Восстановиться из предыдущей копии со статусом OK. 4. Проверить носитель; при необходимости заменить. 5. Создать новую копию (`backup`). **Результат:** есть минимум одна корректная копия, `verify` — «повреждено: 0» | CLI программы, средства проверки диска ОС | Внеплановое |
| **ТК-11** | Ошибка при `backup`: «Хранилище истории не найдено» или «Резервные копии не найдены» при `restore` | 1. Проверить пути `--data-file` и `--backup-dir` и текущий каталог. 2. Если истории ещё нет — выполнить `find … --save`. 3. Повторить команду с корректными путями. **Результат:** команда выполнена, код 0 | CLI программы | Внеплановое |
| **ТК-12** | Не запускается программа: `ModuleNotFoundError: perfect_numbers`; нечитаемая кириллица | 1. Запускать из корня проекта с `PYTHONPATH=src` (PowerShell: `$env:PYTHONPATH="src"`) или выполнить `pip install -e .`. 2. В Windows для кодировки: `chcp 65001`. 3. Проверить версию Python ≥ 3.10. **Результат:** программа запускается, сообщения читаемы | Python, консоль ОС | Внеплановое |
| **ТК-13** | Ошибка диапазона или нехватка ресурсов: «Длина диапазона не должна превышать…», слишком долгий расчёт | 1. Разбить диапазон на окна длиной ≤ 5 000 000 чисел. 2. При нехватке памяти (пик ≈ 47 МБ на максимальное окно) закрыть другие приложения. **Результат:** расчёт завершён, код 0 | CLI программы | Внеплановое |
| **ТК-14** | Тесты или CI упали после изменения кода | 1. Воспроизвести локально: `python -m unittest discover -s tests -v`. 2. Найти коммит, вызвавший сбой (`git log`, `git bisect`). 3. ## 3. Контроль качества и отчётность

### 3.1 Параметры контроля

Стабильность ПС и качество проведения работ ТО оцениваются по следующим метрикам:

| Параметр | Метод измерения | Целевое значение | Критичное значение |
|---|---|---|---|
| Доля копий, прошедших проверку целостности | `verify`: «повреждено: N» | 100 % (N = 0) | любая повреждённая копия — инцидент ТК-10 |
| Возраст последней корректной копии | `list-backups`: дата создания | не более 1 суток (при активной работе), не более 7 суток (в остальное время) | более 7 суток |
| Число копий в каталоге | `list-backups` | ≤ `--keep` | превышение `--keep` — проверить ротацию |
| Время создания копии (до 1000 записей) | замер при выполнении `backup` | ≤ 1 с (измерено ≈ 5 мс) | > 5 с |
| Время расчёта диапазона 1…1 000 000 | замер при выполнении `find` | ≤ 10 с (измерено ≈ 1,1 с) | > 30 с |
| Результат автотестов | `unittest discover` | 68 из 68 | любой провал |
| Статус CI | GitHub Actions | все задания зелёные | красный статус на `main` |
| Время восстановления после сбоя (RTO) | от обнаружения до успешного `restore` | ≤ 15 минут | > 1 часа |
| Допустимая потеря данных (RPO) | возраст последней корректной копии на момент сбоя | ≤ 1 суток | > 7 суток |
| Своевременность плановых работ | выполнение карт ТК-01…ТК-08 в срок | 100 % | пропуск ТК-01 или ТК-02 |

### 3.2 Порядок оценки

1. Исполнитель выполняет работы по технологическим картам в указанные сроки.
2. Проверяющая оценивает параметры контроля из п. 3.1 и соответствие выполненных работ картам.
3. При выходе параметра за целевое значение проводится внеплановое ТО по соответствующей карте раздела 2.2; при достижении критичного значения — работы по ТО выполняются немедленно.
